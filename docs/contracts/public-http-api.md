# Public HTTP API Contract

This document defines the complete API contract between the frontend and backend for the one-time-link application.

API field naming, crypto defaults, payload limits, and encoding rules are defined in `crypto-and-api-decisions.md`.

## Base Configuration

**Local Development:**
- Base URL: `http://localhost:8080`
- CORS Origin: `http://localhost:5173`

**Production:**
- Base URL: `https://api.secret.quorix.io.vn`
- CORS Origin: `https://secret.quorix.io.vn`

**Global Headers:**
- `Content-Type: application/json` (for POST requests)
- `X-Request-ID: <uuid>` (generated by client or server, echoed in response)

**Current Status (Milestone 4 Complete):** All endpoints fully implemented with rate limiting, enhanced error handling, and production-ready features.

## 2. Create Secret

### Request
```http
POST /api/secrets
Content-Type: application/json

{
  "ciphertext": "base64-encoded-encrypted-data",
  "nonce": "base64-encoded-96-bit-nonce",
  "algorithm": "AES-GCM", 
  "ttlSeconds": 3600
}
```

**Field Specifications:**
- `ciphertext`: Base64url-encoded encrypted secret (max 15KB after encoding)
- `nonce`: Base64url-encoded 96-bit nonce (exactly 16 characters)
- `algorithm`: Must be exactly "AES-GCM"
- `ttlSeconds`: Must be one of: 3600, 86400, 604800
- `content`: Not accepted by the public API. Plaintext must be encrypted in the browser before submission.
- `burnAfterRead`: Optional. If provided, it must be `true`; `false` is rejected because all public links are one-time links.

**Implementation Status:** ✅ Fully implemented with ciphertext-only validation and rate limiting (120 requests/hour per IP).

### Success Response (201)
```json
{
  "secretId": "AbCdEfGhIjKlMnOpQrStUv",
  "token": "AbCdEfGhIjKlMnOpQrStUv",
  "url": "/AbCdEfGhIjKlMnOpQrStUv",
  "expiresAt": "2026-04-16T13:00:00Z"
}
```

**Note:** Field names use camelCase as per API naming convention.

**Error Responses**

**Rate Limited (429):**
```json
{
  "error": "rate_limit_exceeded",
  "message": "Too many requests. Please try again later.",
  "details": {
    "retry_after": 3600

  "timestamp": "2026-04-16T12:00:00Z",
  "request_id": "uuid"
}
```

**Invalid Request (400):**
```json
{
  "error": "validation_failed",
  "message": "Request validation failed",
  "details": {
    "validation_errors": [
      {
        "field": "ttlSeconds",

  },
  "timestamp": "2026-04-16T12:00:00Z",

```

Plaintext submission is rejected:

```json

```

**Payload Too Large (413):**

```json
  "message": "Request body exceeds maximum size of 15KB",
  "timestamp": "2026-04-16T12:00:00Z",
```

## 4. Open Secret (Reveal)

### Request
```http
POST /api/secrets/{secret_id}/open
Content-Type: application/json

{}
```

`POST /api/secrets/{secret_id}/consume` remains available as a backward-compatible alias.

**Path Parameters:**
- `secret_id`: Opaque base64url token returned as `secretId` by the create endpoint

**Request Body:** Optional empty JSON object. The backend ignores the body; the frontend currently sends `{}` for consistency.

**Reveal Session Header:** Optional `X-Reveal-Session` header. When present, the backend verifies the session before consumption.

**Implementation Status:** ✅ Fully implemented with Redis claim/finalize one-time semantics and rate limiting (240 requests/hour per IP).

### Success Response (200)
```json
{
  "secretId": "AbCdEfGhIjKlMnOpQrStUvWxYz0123456789abcd",
```

## 5. Create Reveal Session

### Request
```http
POST /api/reveal-sessions
Content-Type: application/json

{
  "secretId": "AbCdEfGhIjKlMnOpQrStUvWxYz0123456789abcd"
}
```

**Path Parameters:** None

**Request Body:** Required JSON object with `secretId`.

**Implementation Status:** ✅ Fully implemented as a lightweight reveal handshake with rate limiting (240 requests/hour per IP) and a 15-minute session TTL.

### Success Response (201)
```json
{
  "sessionId": "c2Vzc2lvbi1pZC1iYXNlNjR1cmw",
  "secretId": "AbCdEfGhIjKlMnOpQrStUvWxYz0123456789abcd",
  "status": "active",
  "expiresAt": "2026-04-16T12:45:00Z"
}
```

### Error Responses

**Invalid Secret ID (400):**
```json
{
  "error": "invalid_secret_id",
  "message": "Secret token is invalid"
}
```

**Not Found / Expired / Consumed:**
```json
{
  "error": "SECRET_NOT_FOUND",
  "message": "No secret letter was found here.",
  "timestamp": "2026-04-16T12:30:00Z",
  "request_id": "uuid"
}
```

### Reveal Session Usage
- `POST /api/secrets/{secret_id}/open` accepts the optional `X-Reveal-Session` header.
- When provided, the backend verifies that the session matches the secret before consumption.
- If the header is omitted, the endpoint still works for backward compatibility.

## 6. Error Response Format

All error responses follow this consistent structure:

```json
{
  "error": "error_code",
  "message": "Human-readable error description",
  "details": {},
  "timestamp": "2026-04-16T12:00:00Z",
  "request_id": "req_123e4567-e89b-12d3-a456-426614174000"
}
```

**Common Error Codes:**
- `validation_failed`: Request validation failed (includes field-specific errors)
- `rate_limit_exceeded`: Too many requests from this IP
- `payload_too_large`: Request body exceeds size limits
- `invalid_secret_id`: Secret token is malformed
- `not_found`: Secret does not exist or has expired
- `already_consumed`: Secret has been previously revealed
- `SECRET_CONSUMED`: Secret has been previously revealed
- `SECRET_EXPIRED`: Secret has expired
- `SECRET_NOT_FOUND`: Secret does not exist
- `internal_error`: Server-side error (details not exposed)

**Implementation Status:** ✅ All errors follow structured format with AppError type and field-specific validation.

## 10. Implementation Notes

**Implementation Status:** ✅ All features fully implemented

**Fragment Key Handling:**
- The decryption key in URL fragments (`#key`) is never sent to the server
- Frontend must extract and use fragment key for client-side decryption
- Frontend must reject missing or malformed fragment keys before calling the open endpoint
- Server never logs or processes fragment keys

**Request ID Tracking:**
- Frontend should generate UUID v4 for `X-Request-ID` header
- Server echoes this ID in response headers and logs
- Useful for debugging and request correlation
- All error responses include request ID

**Atomic Operations:**
- Secret consumption uses a Redis claim/finalize flow
- Prevents race conditions between concurrent reveal attempts
- First successful open wins, subsequent attempts get `SECRET_CONSUMED`

**Performance:**
- Health and readiness responses use `Cache-Control: no-store`
- Request metrics tracked for monitoring
- Slow requests (>100ms) logged for analysis
- P95 latency < 100ms, throughput 100+ req/s

**Error Handling:**
- All errors follow structured format with AppError type
- Field-specific validation errors included in details
- Multiple validation errors returned together
- Error logging with context (no sensitive data)
- 4xx errors logged as info, 5xx as error
